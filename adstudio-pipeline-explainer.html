Why your generated ad looks nothing like the template

An interactive trace of the actual code path: how a template is built (deterministic, in code) and how the “Generate” button makes an ad (an AI image call that never sees the template). Click any stage to open the real payload. The playground reproduces your selectLayoutArchetype / geometryForArchetype logic in the browser.

A “template” is a copy object, not a picture

The thing called a template in AD_STUDIO_TEMPLATES has no visual layout at all — just an id, a goal, an offer and a one-line promptHint. The picture you see in the editor is assembled separately by deterministic layout code. Walk the chain:

STEP 1 — the template is pure text/metadatasrc/lib/adstudio/templates.ts

Every template is this shape. Note: no layout, no colours, no image, no positions.

{
  id: "just_listed",
  name: "Just listed",
  goal: "seller_leads",
  offerId: "home_value_update",
  promptHint: "Promote a newly listed property and invite local owners to compare their own home."
}

There are 10 of these. promptHint is the only free text — and it drives copy, never the image.

STEP 2 — id is mapped to 1 of 8 visual archetypeslayout-archetypes.ts

The visual identity lives here, keyed off the template id (with regex fallbacks on name/offer/goal):

just_listed | new_to_market  → listing_hero
coming_soon                  → coming_soon
open_home                    → open_home
just_sold                    → just_sold
market_update                → market_stat
price_update | free_appraisal→ appraisal
seller_checklist             → seller_guide
buyer_demand                 → social_proof

So 10 templates collapse onto 8 layout archetypes. This is the entire “look” system.

STEP 3 — archetype → exact pixel positionsgeometryForArchetype()

Each archetype sets margins, copy block position/width, headline size, scrim opacity, and any support shape (announcement band, details panel, sold ribbon, market side-panel, value panel…). Example for a 1:1 canvas (1080×1080), appraisal:

marginX 86 · copyX 86 · copyY 518 · copyWidth 756
headlineSize 64 · subheadSize 28 · scrim rgba(7,14,25,0.42)
support: value_panel @ (52, 474, 832×520)  // dark glass panel

This is 100% deterministic. The same template always lays out the same way. The playground in tab 3 runs this exact math.

STEP 4 — layers are stacked into a canvasbuildArchetypeCreative()

Objects are pushed bottom-to-top. Your uploaded photo is just one layer (primary_image), full-bleed, with a dark scrim over it and text on top:

background        (brand secondary colour fill)
primary_image     ← the user's uploaded photo (or a brand stock image)
image_scrim       (dark overlay so text is readable)
[support shapes]  (panel / band / ribbon for this archetype)
headline (text)   subhead (text)
cta_button + cta_text
brand_logo

The headline/subhead text comes from the copy generator (generator.ts → buildFirstAdMessages), themed by template name.

STEP 5 — rendered to SVG you can see + Fabric JSON you can editrenderer.ts / creative-design-json.ts

renderCreativeSvg() turns the canvas objects into previewSvg; fabricJson (version blockwise-fabric-v1) is the editable version. This SVG is the faithful templated ad. It matches the template because it is the template — built in code, not by a model.

Takeaway: nothing here calls an AI image model. The template render is exact and reproducible. The mismatch starts in tab 2.

Two tracks that never talk to each other

When you hit “Generate background” the app does not render the template through a model. It runs a separate text-to-image call, then drops the result into the template’s image layer. The template’s layout, its copy positions, even your uploaded photo — none of it is described to the image model.

Track B · the AI image call

Runs on a model. Produces a brand-new stock-style photo, then overwrites the image layer.

B-1 — the prompt is just concatenated copyad-studio-workbench.tsx
prompt: [copy.headline, copy.description, market, propertyType,
         "real estate advertising background"]
        .filter(Boolean).join(" | ")

No layout, no archetype, no co-ordinates, no reference image. Two different templates with similar copy produce almost identical prompts → almost identical generic photos.

B-2 — assembled into system/brand/negative textassemble-prompt.ts → assembleImagePrompt()

Wraps the string with image system prompt, brand constraints (colours/style tags), a negative prompt and aspect-ratio rules. referenceAssets are formatted as text descriptions only (formatReferenceAssetContext → “Asset 1: image/png data URL (… bytes)”) — never as pixels for OpenAI.

B-3 — provider sees text; OpenAI never sees an imageai-providers.ts

OpenAI (gpt-image-2) is a pure text-to-image endpoint here — the body is {model, prompt, size, quality, n}. Reference images are appended to the prompt as a text line and discarded as pixels.

OpenRouter (Gemini) can accept image_url parts — but the background-generate path sends referenceAssets: [], so even there your photo isn’t attached.

// buildImagePrompt(): everything flattened to a string
[input.prompt, "Aspect ratio: …", "Style preset: …",
 "Avoid: …", "Reference assets: <url>."].join("\n")
B-4 — generic photo replaces your image layerad-studio-workbench.tsx → generateBackgroundImage()

setPrimaryImage(json.image) swaps the model’s output into the primary_image slot. The template chrome (text/CTA/logo) stays, but the photo is now a generic AU streetscape that ignores your listing and the template’s intent — hence “same shitty ad.”

The break-point — and how to close it

Four concrete disconnects, each grounded in a file. Click to expand. The fixes are ordered by impact.

1

The image model never receives the template layout

It gets a flat copy string + brand colours. No archetype, geometry, copy-safe regions, or composition.

ad-studio-workbench.tsx → generateBackgroundImage() builds the prompt from copy only; generate-image/route.ts has no templateId param at all.

Fix: pass the archetype + a layout brief into the prompt — “hero photo with the lower-third left clear for a headline panel; subject framed top-right; horizon at 40%.” Even as text this steers composition toward the template. Derive it from geometryForArchetype() so the photo leaves room exactly where the scrim/panel/text sit.
2

Your uploaded photo isn’t sent to the model

Background-generate passes referenceAssets: []; OpenAI can’t take an image input here anyway.

generateBackgroundImage() omits referenceAssets; ai-providers.ts OpenAI body is text-only; OpenAI reference assets are stringified by formatReferenceAssetContext.

Fix: for image-conditioned edits, route through the provider that accepts image_url parts (OpenRouter/Gemini path already supports multiReference) and actually pass the listing photo as a reference asset — or use an image-edit/inpaint endpoint so the model preserves the real property instead of inventing a new one.
3

Every template funnels into near-identical prompts

10 templates → 8 archetypes → but the image prompt only uses headline + description + suburb + “real estate advertising background.”

The richer, archetype-specific prompt language already exists in bulk-cell.ts → buildImagePrompt() (AU-specific cues, composition, lighting, copy-safe space) — but the interactive workbench path doesn’t use it.

Fix: reuse the bulk-cell prompt builder (or its styleDescriptor) in the workbench so each archetype emits a distinct, art-directed prompt instead of the one-line concat.
4

“On-template” is a render job, not a generation job

The template already composites perfectly in code. The model’s only honest job is the photo inside the frame.

Track A (renderCreativeSvg) is faithful by construction. The mismatch is purely that the Track B photo ignores the template.

Fix / reframe: keep generation scoped to “produce a photo that fits archetype X with copy-safe zone Y,” then let the deterministic renderer place text/CTA/logo as it already does. Don’t ask the model to reproduce the whole ad — ask it for a layer the template can hold. This also makes the earlier 504/timeout debate moot: a single, well-scoped photo call is short.

In one sentence

The template is built deterministically in code and is always on-brief; the “Generate” button runs a separate text-to-image call that is never told about the template or shown your photo — so it returns a generic stock image that the app drops into the template frame. Fixing it means feeding the archetype/layout (and the real photo) into the image call, or scoping the model to just the photo layer the template already knows how to place.
